# Madinimarket

Madinimarket is a full-stack marketplace for buying and selling minerals in Tanzania and beyond. The website combines a public mineral marketplace with buyer and seller accounts, order processing, subscriptions, private offers, and admin and staff workspaces. It is built with Next.js, React, TypeScript, and Supabase.

## Current website features

- **Public marketplace:** Browse approved mineral listings and buyer requests, search by mineral or location, and view market content when the admin-configured weekly schedule is open. The welcome hero appears after an admin adds its headline and copy, links visitors directly to mineral listings and buyer requests, and can display up to three rotating background images. Only admins can hide or show the hero or edit its copy and design; staff Homepage Display permissions do not include hero visibility. The admin controls whether USD is available alongside TSh.
- **Buyer and seller accounts:** Website accounts use generated `MM-####` usernames. Sellers manage their listings and buyer requests, submit dealer/broker licence documents, and manage subscriptions. Buyers can shop from listings, manage their orders, and receive or respond to private offers.
- **Submissions and subscriptions:** Seller listings and buyer requests are reviewed before appearing publicly. Seller/buyer subscriptions are managed through payment instructions, payment-reference and receipt submission, and admin or authorized staff review.
- **Orders and Cart:** Signed-in users can manage their cart, private offers, active buying and selling orders, and order history. The purchase workflow supports seller availability checks, manual payment verification, shipping details, delivery confirmation, buyer receipt, disputes, refunds, and seller payouts.
- **Private offers:** Eligible sellers can make offers on buyer requests. Accepted offers continue through the standard order workflow without publishing the private mineral as a public listing.
- **Help and support:** Website users can submit support requests and attachments and continue the conversation from their account. Admins and staff with Support Inbox access respond through the support workspace.
- **Admin and staff workspaces:** Admins configure and review marketplace operations. Staff see only the workspaces allowed by their assigned roles; queue counts help identify pending tasks.

The sections below describe local development, Supabase setup, the order lifecycle, private offers, and account data. This is a marketplace and accounting workflow, not an escrow service or automatic payment-transfer system.

## Run locally

```bash
npm install
npm run dev
```

Open [http://localhost:3000](http://localhost:3000).

Run a production build with `npm run build` and lint with `npm run lint`.

## Supabase setup

Configure the Supabase project and run these scripts in order in the Supabase SQL editor:

1. Copy `.env.example` to `.env.local`.
2. Add your Supabase project URL and keys.
3. Run `supabase/schema.sql`.
4. Run `supabase/approval-workflow.sql`.
5. Run `supabase/currency-control.sql` to add or upgrade the marketplace currency setting.
6. Run `supabase/platform-pricing.sql` to enable the admin-managed mineral listing fee.
7. Run `supabase/subscription-control.sql` to add account subscription plans and marketplace visibility controls.
8. Run `supabase/subscription-no-renew.sql` after `subscription-control.sql` if setting up a fresh project.
9. Run `supabase/subscription-payment-proof.sql` after `subscription-control.sql`; if `subscription-no-renew.sql` has been run, apply this migration afterward. It adds private PDF/JPEG/PNG receipt storage (up to 4 MB), payment references, and admin rejection reasons. It also prevents requesting or approving another subscription while an account has an active or scheduled term. Re-run it after updates. Also run `supabase/marketplace-payment-instructions.sql` before users submit subscription payments.
10. Run `supabase/certificate-verification.sql`.
11. Run `supabase/translation-dictionary.sql`.
12. Run `supabase/homepage-content-settings.sql` to allow admin control of the Swahili switch, rotating homepage phrases, headline font size, and welcome-hero visibility and design. It also creates the public `homepage-hero` storage bucket for JPEG, PNG, WebP, and AVIF images up to 20 MB each; upload tokens are issued only through the admin-only application API. Existing installations must run `supabase/homepage-hero-original-image-uploads.sql` before deploying original-quality hero uploads. Re-run this idempotent script on existing installations before deploying hero customization updates; it clears only the original, untouched welcome-hero copy defaults, adds the default height mode and button-position settings to existing settings, and preserves customized settings.
    Before deploying the Marketplace Cards panel, run or re-run `supabase/marketplace-card-column-settings.sql`. It adds the seller/buyer card appearance settings alongside the existing card-column controls.
13. Run `supabase/market-hours.sql` after the other scripts so public listing and request views enforce the weekly market schedule.
14. Run `supabase/live-refresh.sql` to enable Realtime change notifications for public listing and buyer-request updates.
15. Run `supabase/marketplace-orders.sql` to add the mineral cart, purchase orders, availability/payment/shipping workflows, and payout records. Re-run this idempotent script after updates so existing installations receive new order-notification fields.
16. Run `supabase/marketplace-order-shipments.sql` after `supabase/marketplace-orders.sql` to group eligible paid, unshipped items by order and seller when tracking is submitted, and to confirm delivery and buyer receipt once per tracking group. Existing tracked or shipped items are not changed. Disputes and payout amounts remain item-level; payout recording can share one transaction reference and receipt for eligible items with the same order, seller, tracking details, and bank snapshot.
    Before deploying the early buyer receipt flow, run `supabase/marketplace-order-early-receipt.sql` in the production Supabase SQL Editor. It records buyer receipt separately from carrier verification, prevents new disputes after receipt is confirmed, and still requires admin/staff delivery confirmation before seller payout.
17. Run `supabase/marketplace-seller-payout-receipts.sql` after `supabase/marketplace-orders.sql` to add private PDF/JPEG/PNG receipt storage (up to 4 MB) for completed seller payouts. The admin attaches a receipt when recording a payout; only the seller for that order and admins receive signed links. Items included in the same seller payout batch share the receipt and transaction reference, shown together in Admin Marketplace Orders and the seller’s order history.
18. Run `supabase/marketplace-admin-order-queue.sql` after `supabase/marketplace-orders.sql` to support the admin marketplace order queue with search, status filters, action-first ordering, and server-side pagination.
    For existing installations, run or re-run `supabase/marketplace-admin-order-processing-scope.sql` in the production Supabase SQL Editor before deploying staff order permission changes. It provides the full active order-processing queue and keeps delivery confirmation, disputes, and buyer refunds in their separate queues. Run this script after `marketplace-admin-order-queue.sql`; both scripts must use the current five-argument queue function, including the staff email-search restriction.
    Re-run both `supabase/marketplace-admin-order-queue.sql` and `supabase/marketplace-admin-order-processing-scope.sql` in that order before deploying staff order updates or staff contact privacy updates.
19. Run `supabase/marketplace-sales-ledger-realtime.sql` after `supabase/marketplace-orders.sql` to publish marketplace order updates to Supabase Realtime and allow authenticated admins (only) to receive them under row-level security. The Seller price ledger refreshes when an order is marked paid, with 60-second polling as a fallback.
20. Run `supabase/marketplace-order-time-limits.sql` after `supabase/marketplace-orders.sql` to add the admin-configurable seller confirmation and buyer payment windows. Re-run this idempotent script after updates. Saving new values recalculates deadlines for pending orders from when each stage began; a deadline already past is expired by the next order scheduler run.
21. Run `supabase/marketplace-payment-instructions.sql` to enable admin-managed buyer payment instructions. The admin can save up to ten reusable payment-method/account-number pairs and a separate general instruction note. After running it, open the admin panel's Buyer payment instructions section and save the approved payment details. Changes apply immediately to all orders still awaiting payment; orders already submitted for payment verification are unaffected. These same instructions are shown to users submitting subscription payments.
22. Run `supabase/marketplace-listing-reservations.sql` to show confirmed-order reservations publicly, hide unavailable listings, let sellers confirm stock before relisting, keep listing reservation state synchronized when order items are updated or deleted, and release stale reservations with no active order item. Re-run this idempotent script after updates so existing installations receive reservation fixes and stale reservations are reconciled.
23. Run `supabase/marketplace-private-offers.sql` to add private offers on buyer requests and connect accepted offers to the standard order workflow. Then run `supabase/private-offer-checkout-window.sql` to reserve inventory when an offer is accepted, enforce the 30-minute checkout deadline, reopen the buyer request and eligible competing offers after expiry, and enable retryable buyer offer emails. Run `supabase/private-offer-fulfilled-request-cleanup.sql` to remove fulfilled requests from buyers’ active wanted-minerals panel and backfill old fulfilled requests that were still marked active.
24. Run `supabase/marketplace-user-post-management.sql` after `supabase/marketplace-orders.sql`, `supabase/marketplace-listing-reservations.sql`, and `supabase/marketplace-private-offers.sql`. It adds guarded permanent deletion and price changes for idle approved seller listings and buyer requests, plus a cart-insert lock that prevents those changes from racing with a new cart item.
25. Run `supabase/website-password-reset.sql` to enable one-time password-reset links for buyer and seller accounts.
26. Run `supabase/support-inbox.sql` before deploying support inbox updates. Re-run it for existing installations to add message read receipts and user-only hide fields. Admins and staff with Support Inbox permission can permanently delete a conversation for everyone; staff must claim the conversation before making changes. When a user deletes a conversation or message, it is hidden only from that user's view and remains available to support staff.
     Before deploying staff contact privacy updates, run `supabase/staff-contact-privacy.sql` in the production Supabase SQL Editor. It removes direct public access to listing and buyer-request contact fields and recreates the public listing feed without email or phone.
27. Add `SUPABASE_SERVICE_ROLE_KEY`, `GMAIL_USER`, `GMAIL_APP_PASSWORD`, and a strong `CRON_SECRET` to the server environment. Never expose the service-role key or cron secret to the browser. Set `GMAIL_FROM` to `Madini Market <info@madinimarket.co.tz>` only after that sender alias is verified in Gmail; otherwise app emails use `GMAIL_USER`. Set `NEXT_PUBLIC_APP_URL` to `https://www.madinimarket.co.tz` for production; app-generated email links reject localhost and fall back to the canonical production URL. Buyer payment instructions are managed and saved in the admin panel, not in an environment variable.
28. Configure an external scheduler to send an HTTP `GET` request to `/api/cron/marketplace-orders` every minute, using the standard HTTP token authorization scheme and the `CRON_SECRET` value. This endpoint expires seller-response, payment, and private-offer checkout windows; hides listings whose sellers do not respond; retries failed seller availability and new private-offer emails; sends timeout notices; triggers the seven-day delivery payout rule; retries unsent transactional emails; and automatically deletes expired unpaid orders 30 minutes after their payment deadline. Buyers can delete an expired order themselves before then. Set the same strong `CRON_SECRET` in the deployment environment and in the scheduler's secret/header configuration. Vercel Hobby does not allow a one-minute cron schedule, so this repository does not configure a Vercel cron; order deadlines, automatic expired-order cleanup, and automatic payout eligibility will be processed late or not at all until the external scheduler is configured.

For staff role setup, run `supabase/staff-management.sql`, `supabase/staff-role-management.sql`, `supabase/staff-role-editing.sql`, and `supabase/staff-task-claims.sql` in that order. Re-run `supabase/staff-task-claims.sql` in the production Supabase SQL Editor to apply claim-performance updates before deploying; the claim RPC replaces expired claims for the requested task without sweeping the entire claims table on each click. After the subscription and staff role scripts are installed, run `supabase/staff-permissions-v2.sql`. On an existing installation, run this migration in the production Supabase SQL Editor before deploying the matching application update. It replaces the old Accounting permission with Marketplace Orders Processing and expands Market Moderation into Seller Submission Reviews and Buyer Submission Reviews while preserving existing access. Then run `supabase/staff-account-permissions.sql` after `staff-permissions-v2.sql`. It adds separate, default-off switches for activating/deactivating and permanently deleting buyer/seller accounts. These switches appear only on roles with Seller/Buyer Accounts permission; admins retain access regardless of the switches, and staff still need to claim each account task. Run `supabase/staff-account-role-scope.sql` after `staff-account-permissions.sql` and before deploying this UI correction; it enforces that account action permissions stay on account roles. Run `supabase/staff-account-permission-cleanup.sql` to remove legacy account-action permissions from non-Accounts roles. Account creation, non-admin sign-in suspension, and sign-out-all controls remain admin-only. Role permission changes are recorded in the staff audit log. Role permissions are Seller/Buyer Accounts (account list and account tasks), English–Swahili Translations, Homepage Display, Marketplace Orders Processing, Delivery Confirmation, Order Disputes, Buyer Refunds, Activate/deactivate buyer/seller accounts, Permanently delete buyer/seller accounts, Seller Submission Reviews, Buyer Submission Reviews, Subscription Payment Confirmations, and Support Inbox. Subscription Payment Confirmations does not grant permission to add or edit plans.

Run `supabase/staff-role-unassign.sql` to allow a staff member to have no assigned roles. Apply it in the production Supabase SQL Editor before deploying code that enables saving an empty role selection. Staff without roles cannot access permission-controlled work but can still contact the admin through staff chat.

The admin currency switch controls whether new seller listings and buyer requests can use USD. The database keeps existing USD records unchanged and rejects new or currency-edited USD records while USD is disabled. The admin listing fee setting applies to new mineral listings; each listing keeps its saved fee rate and price when the setting changes. The admin market-hours schedule repeats weekly in East Africa time; its default keeps the market open until an admin saves a schedule. When closed, public listing and buyer-request views return no records.

The admin order time limits panel sets whole-hour seller confirmation and buyer payment windows (1–168 hours). Saving applies the new durations to pending orders, recalculating from the start of each stage; an already elapsed deadline is processed by the next scheduled order check.

The admin English–Swahili panel controls whether visitors can switch to Swahili. Homepage headline phrases have their own admin panel; enter regular and highlighted parts separately, then set the headline size from 24 to 72 pixels. Saved phrases rotate every minute and are hidden when none are saved; the font size scales down on narrow screens.

The Homepage Display panel’s welcome-hero editor is admin-only. It supports editable hero copy, separate colors for the Sell a mineral and Post a request buttons and their text, adjustable background opacity, border color and width, and shadow strength for each button, editable labels for the Explore minerals and buyer-browse text links (blank by default; links appear when labeled), and independent horizontal and vertical positioning for the headline/description, each button, and links on desktop and phone. Elements can overlap, so use the live preview to position them clearly. The editor also supports serif/sans font, weight, heading sizes, three height modes (Default, Fit available screen, and Full screen), and up to three synchronized JPEG, PNG, WebP, or AVIF background slides. Each slide has its own headline and description, and admins can choose Appear, Fade, Fly in, Slide, Split, Shape wipe, Wheel, Random bars, Grow and turn, or Zoom transitions for the image and copy. They can set the slide interval from 5 to 30 seconds (default 10) and the transition duration from 0.5 to 3 seconds (default 1). The built-in gemstone artwork is used only when no desktop slides are configured. Each slide can have an optional phone-specific original image, with independent focal-point and zoom controls for desktop and phone; without one, the desktop original is displayed with the phone focal point and zoom. The homepage serves the original uploaded files directly; focal points affect display only, and the original bytes are not cropped or re-encoded. The live preview and resolution warning help admins adjust focal points and identify sources that may look pixelated when enlarged. Saving settings removes any legacy generated-crop references and cleans up their files. The editor previews both layouts at representative desktop and phone sizes. The hero has no default copy and stays off the public homepage until an admin saves a headline; if homepage settings have not loaded, it does not display placeholder text. Original image files are uploaded directly to storage and can be up to 20 MB each. Discard leaves the published site unchanged. Saved slides pause while the browser tab is hidden and respect reduced-motion preferences. Existing production databases must run `supabase/homepage-hero-original-image-uploads.sql` before deploying this change. Existing `exploreLabel` values are migrated to the Sell button label when possible, and positioning and link labels use the existing JSON settings without a new database column.

Open marketplace pages refresh when they become visible or reconnect, poll for changes as a fallback, and use Supabase Realtime notifications to refresh listings and buyer requests. The admin Seller price ledger refreshes on Realtime marketplace-order updates when payment is verified, with authenticated API polling every 60 seconds as a fallback. Other private settings and administrator data continue to refresh through authenticated API polling. A version notice appears when a newer deployment is detected; users can reload when ready so an open form is not lost.

Buyer and seller accounts are stored in `public.website_accounts`; their passwords are hashed by the server and they do not appear in Supabase Auth. The admin must be created in Supabase Auth and have a matching `public.profiles` row with `role = 'admin'`. Admin usernames can be any value; `MM-####` usernames are reserved for buyer and seller accounts. Admins can request a password recovery link from the sign-in dialog using their profile username and registered email; the link opens a password reset form rather than signing them straight into the marketplace.

Admins manage subscription plans from the Seller/buyer subscription panel. Website users see the admin-managed payment instructions, pay outside the site, then submit their plan, transaction reference, and receipt only when they have no active or scheduled subscription. Receipts are private in Supabase Storage; administrators receive temporary signed links for review. An admin confirms or rejects the payment and provides a reason when rejecting it. Confirmation starts the subscription immediately; users can request another plan after the current term expires. Each subscription month is exactly 30 days, and approved listings and buyer requests from website accounts are visible only during an active subscription.

Active subscription plan prices are readable through the public Data API. Subscription records remain private: only the server's service-role API can access them; do not grant anonymous or authenticated CRUD access to `account_subscriptions`.

## Mineral purchase workflow

- New website accounts collect a delivery address; existing accounts can fill or correct it when confirming their first order. The buyer's saved name, phone, and delivery address are snapshotted to each order. The seller receives the buyer name, phone, and address only after an administrator verifies payment; the buyer email is not included.
- Adding a mineral to a cart does not reserve it. Confirming the order reserves each listing, disables further cart additions, and publicly shows “Temporarily reserved — availability being confirmed” until the seller responds. Sellers have six hours to respond. A seller-confirmed unavailable item or a non-response is hidden from the public market and remains in the seller's order history; sellers can confirm the stock and relist it from My orders. Unavailable items are removed from the order, and the two-hour payment period starts after seller responses are finalized. Orders use one currency at a time.
- Buyers submit a payment transaction reference. An administrator verifies payment manually before sellers are instructed to dispatch. Sellers record the carrier and tracking number. An administrator checks the carrier's tracking and marks delivery confirmed; the buyer may confirm receipt or open a dispute.
- Receipt confirmation makes the seller payout due. If the buyer does not confirm, the scheduled job makes the payout due seven days after the administrator records carrier-confirmed delivery, unless the buyer opens a dispute. An administrator resolves disputes per item. Eligible payout-due items sharing an order, seller, tracking details, and bank snapshot can be recorded with one seller transaction reference and receipt; each item's payout amount remains separately accounted for.
- This is manual payment administration, not escrow or an automatic money-transfer integration. Madinimarket must receive and hold buyer funds outside the app, make seller payouts/refunds outside the app, and record those transfers in the admin orders panel. An administrator configures the approved buyer payment destination and steps in the admin panel; edits update all orders still awaiting payment. Configure Gmail SMTP so seller and buyer notifications can be sent. The app does not independently verify a carrier API or transfer funds.
- The admin Seller price ledger keeps submitted listing prices separate from verified sales. Its sales report uses payment verification timestamps and saved order-item amounts to show per-product transactions and current daily, weekly, monthly, and yearly gross sales, seller amounts, and Madinimarket fees in East Africa time. Refunded items are excluded from current summaries. Fee totals are accounting records from the marketplace workflow, not bank reconciliation; confirm actual deposits against external account statements.
- Listings owned by a seller without a website account cannot be purchased through this checkout workflow because that seller cannot respond to availability requests in their account.

## Private buyer-request offers

- An active seller with an approved dealer/broker licence can send a structured mineral offer and private photo from an eligible public buyer request. Buyer and seller review offer cards in the signed-in cart/orders panel; contact email and phone are not displayed in these cards.
- Each seller/request thread allows up to three price offers. A seller must wait for the buyer to decline an offer before sending a revision. Every offer snapshots the current admin-set listing fee, seller amount, fee amount, buyer total, and currency. Sellers see their price and fee breakdown; buyers see only the all-in total.
- The buyer can accept or decline an offer. After acceptance, the seller confirms the final mineral details without changing the agreed price or currency; the buyer reviews the final card and confirms the delivery details to create a standard marketplace order. The private mineral is not published as a public listing.
- Private orders use the same seller availability response, two-hour payment window, manual payment verification, shipping, receipt, dispute, and payout workflows as public market orders. An active or completed order prevents another checkout for the same buyer request, closes that request’s competing offers, and reserves the same seller’s matching private mineral card across requests. The saved fee and seller amount are carried into the order item. This remains manual payment administration; it does not automatically hold funds or transfer the seller payout.

## Account and data model

- Buyer and seller accounts sign in to the website using generated `MM-####` usernames; they are not Supabase Auth users.
- Buyer and seller account recovery emails go to the account's registered email and contain a single-use link that expires after 30 minutes. The user sets a new password on the site; passwords are never emailed. Apply `supabase/website-password-reset.sql` before deploying this flow. Administrator account recovery remains managed through Supabase Auth.
- Only the admin signs in through Supabase Auth. The server checks the profile's admin role before issuing a Supabase session.
- Website users can submit and manage their own pending or rejected requests; the admin reviews submissions using the Supabase-backed queue.
- Website users must submit an approved dealer or broker licence before they can list a mineral. Licence files are private and accept PDF, JPEG, or PNG up to 10 MB; admin rejection requires a reason before the user can replace and resubmit a licence.

## Admin and staff workspaces

- **Admin:** The admin manages seller/buyer accounts, listing and request reviews, subscription plans and payment decisions, buyer payment instructions, market hours, currencies, listing fees, order time limits, order processing, delivery confirmation, disputes, refunds, the sales ledger, translations, homepage content, staff roles, and support.
- **Staff:** Staff access is role-based. The admin assigns permissions for seller/buyer accounts, submission reviews, subscriptions, marketplace order processing, delivery confirmation, order disputes, buyer refunds, support, translations, and homepage display. Separate permissions govern account activation/deactivation and permanent account deletion. Account creation, non-admin sign-in suspension, and sign-out-all controls remain admin-only.
- **Separate queues:** Order processing, delivery confirmation, open disputes, and buyer refunds are separate staff workspaces. The staff menu shows each dispute or refund queue count only to staff assigned that permission, including `0` when the queue is empty. The admin menu is not changed by these staff-only counts.
- **Task claims:** Where a staff action requires a claim, staff claim the task before acting. The interface shows who is handling a claimed task and enables the relevant action controls only for the staff member holding the claim. Staff can release a claim when finished or when another staff member should take over.
- **Support:** Website users can create support requests with a category, subject, message, and optional PDF/JPEG/PNG attachments. Admins and staff with Support Inbox permission can reply; staff must claim a conversation before changing it. Conversation and message deletion by a user hides the content only from that user's view, while staff/admin deletion removes a conversation for everyone.
